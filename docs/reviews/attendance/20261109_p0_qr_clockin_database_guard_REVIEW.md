## Changes

1. `supabase/migrations/20261109120000_attendance_qr_clockin_window_guard.sql`:
   - New `SECURITY INVOKER` trigger function `public.enforce_qr_clock_in_shift_window()` executed only before new QR `checked_in` inserts, regardless of which RPC writes the row.
   - Rejects QR inserts without resolved `weekly`/`override` scheduling snapshot or timestamps.
   - Enforces scan `checked_in_at >= scheduled_start_at - interval '60 minutes'` AND `checked_in_at < scheduled_end_at` on absolute timestamps. This preserves valid overnight and split windows while refusing midnight opening-shift inserts.
   - A rejected insert aborts the entire transaction; the stale-close and new-check-in combination cannot partially commit.
   - Grants EXECUTE on internal trigger function to `service_role` only.
   - Guarded branch settings update to 60 minutes; unexpected preexisting settings cause migration to FAIL for review instead of silently replacing a different policy.
2. `tests/database/p0-attendance-qr-clockin-window-guard.sql`:
   - Isolated TEST-only temporary table and trigger harness under transaction+rollback; tests exact boundary, invalid midnight, missing schedule, late scans, overnight/split, and manual-review path.
3. `tests/database/p0-attendance-qr-clockin-window-verify.sql`:
   - READ-ONLY post-install inspection of settings, trigger, function privileges.

**Scope preserved:** no changed columns, table records, RLS, existing attendance RPC definitions, dynamic last-service clock-out function, shift approval logic, booking, payroll, or Desktop code. Existing QR device/branch authorization stays server-side. No override to service-role privileges of the two existing RPCs.

## Source-of-truth and limitations

The trigger checks the server-resolved `scheduled_start_at` and `scheduled_end_at` persisted with a QR write. It does not independently re-run the canonical weekly/override resolver; schedule-source authorization remains in the server scanner. This is a deliberate narrow fail-safe for the proved P0 temporal bypass, **not** full database-only schedule/branch authorization. Independent review must explicitly accept this boundary or request a stronger DB contract before release.

The branch was authored via GitHub because the checked-out repository and Supabase CLI are unavailable in this environment. The migration filename was not generated by `supabase migration new`; repository maintainers must verify/migrate packaging with their active CLI workflow, without altering historical migration history.
