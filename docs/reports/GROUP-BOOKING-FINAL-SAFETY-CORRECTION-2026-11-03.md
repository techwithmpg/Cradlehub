## Accepted lifecycle and proven gap

The public server action quotes/matches therapists and calls `create_booking_order_atomic` as `service_role`. That one transaction creates the order, attendees, all service lines, and price snapshots. Online lines start `pending_crm_confirmation` with `resource_id = NULL`. The accepted `crm_booking_row_blocks_availability` treats that pending state as a therapist reservation; `guard_booking_assignment_overlap` serializes overlapping staff and non-null room allocations with advisory transaction locks. CRM `confirmCrmBooking` authorizes the actor and branch, then calls `confirm_online_booking_order_atomic`, which locks the order and lines and updates every pending line in one database transaction. The accepted confirmation checks active staff and branch service, but it does not allocate rooms, check current qualification/shift, or return the underlying failure reason to the CRM.

The identity-verified disposable **LOCAL TEST** PostgreSQL 17.11 database `group_booking_test` on `127.0.0.1:55434` was built from a minimal schema plus the exact accepted function and booking trigger definitions extracted from the named source migrations. No historical migration chain was replayed. Before the correction, two concurrent-time five-guest public groups with distinct therapists both confirmed across five one-capacity rooms, leaving all ten confirmed lines with `resource_id = NULL`: `ACCEPTED_CONTRACT_ROOM_GAP_REPRODUCED`. This proves a forward confirmation correction is necessary; null rooms on *pending* requests alone do not indicate a defect.

## Local correction and compatibility

The forward migration `20261103015926_confirm_online_booking_capacity_atomic.sql` replaces only `confirm_online_booking_order_atomic`. It preserves its signature, service-role-only EXECUTE, security-invoker mode, order/line locks, pending-to-confirmed lifecycle, replay response, and single-transaction rollback. It takes short SHARE locks on operational staff/schedule/service/room configuration tables before the order row lock, so concurrent configuration edits finish before validation or wait until confirmation commits. It rechecks active services, operational staff (including archive/merge and scheduling metadata), hard-excluded staff roles, explicit service capability, date overrides, multiple active shifts, blocked times, and room availability. For in-spa lines it assigns active branch rooms under the accepted overlap trigger; home-service lines retain the prior no-room contract. If any line cannot be assigned, the database rolls back every status and room change and returns a specific reason. For unassigned groups with insufficient room capacity, the reason includes available and required counts. A preassigned pending room is respected and never silently substituted.

The CRM error mapper translates only known SQL contract errors into useful messages, including available/required room counts. Unrecognized SQL diagnostics remain hidden. Public and CRM guest-count/UI/matching changes from the starting handoff remain intact. A new public guest-tab fallback gives unnamed draft guests visible and accessible `Guest N` labels.

**Affected consumers:** CRM online order confirmation RPC and its CRM action. Public order creation, in-house confirmed-order creation, payment writers, historical migrations, and booking assignment trigger signatures are unchanged. Existing online pending requests can be confirmed through the new function, subject to current capacity. The migration is forward-only; it has not been applied to any Supabase project. A rollback would restore the prior function definition from `20261011020713_p0_booking_security_forward.sql`, but that reopens the demonstrated confirmed-room gap. Operational rollback should disable online confirmations until a corrected function is ready; never clear room assignments from already confirmed bookings.

- **LOCAL TEST confirmation:** the same group sizes all confirmed with a room on every in-spa line; price metadata remained unchanged; confirmation replay changed no rows. Ten guests against five rooms returned `available=5;required=10` and left every line pending with no room. Qualification removal, day-off override, archived staff, hard-excluded role, and multiple-shift scenarios passed. A `service_role` fixture invocation passed.
- **LOCAL TEST concurrency:** two simultaneous five-guest confirmations competing for five rooms produced exactly one fully confirmed group and one fully pending group. Two same-key creation sessions produced one order and ten lines. A room-configuration writer committed before a waiting confirmation; the latter rejected the now-unavailable rooms and left all five lines pending. No partially confirmed group appeared.

These are one-run PostgreSQL `EXPLAIN ANALYZE` measurements on disposable local data, distinct from the pure matcher benchmark and from production latency. Fifty-guest confirmation holds the configuration SHARE locks for about two seconds in this fixture.
