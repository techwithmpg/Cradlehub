## Risk and actual exposure boundary

The classified production catalog recorded `public.staff` owner `postgres`, RLS enabled/not forced, and table ACL `arwdDxtm` for each of `anon`, `authenticated`, and `service_role`. The letters mean SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, and MAINTAIN. Nine additional authenticated column UPDATE ACL entries are redundant while table-wide UPDATE remains granted. Seven authenticated policies grant own/branch/owner reads and constrained owner/operational updates; there is **no anon staff policy**. The SQL `get_auth_role()`/`get_auth_branch_id()` helpers are SECURITY DEFINER, read `staff`, and are used by RLS; the staff branch-sync trigger is also SECURITY DEFINER. Existing trigger creation and maintenance belong to database ownership/migration control, not client request roles.

**Risk classification: high-impact database privilege exposure, exploitability unverified.** PostgreSQL RLS governs row SELECT/INSERT/UPDATE/DELETE but does **not** govern table-wide TRUNCATE or REFERENCES. TRIGGER allows creation of triggers subject to the other applicable SQL permissions; MAINTAIN enables database maintenance and locking operations. These four table grants are unnecessary for accepted request workflows and could matter if a role gains a direct SQL path or an unsafe privileged SQL function. No production exploit, direct database credential exposure, or unauthorized operation was tested or inferred. [PostgreSQL 17 privileges](https://www.postgresql.org/docs/17/ddl-priv.html) and [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) define these boundaries.

Database grants alone do not establish HTTP reachability. Supabase's Data API requires an exposed schema/object, a matching grant, and applicable RLS, while functions have separate EXECUTE privileges. The standard table REST interface uses row CRUD methods; it is not a general SQL/TRUNCATE endpoint. The live Data API settings, schema exposure, direct connection access, and any function-based route were not inspected in this authorized task. [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api), [PostgREST table API](https://docs.postgrest.org/en/stable/references/api/tables_views.html).

## Required workflows and TEST privilege matrix

The scanner's `scan-engine.ts` creates a server admin client for staff/device/QR/attendance reads and writes. Public booking context and tracking handlers also use server admin reads for staff. Staff onboarding uses the admin client for staff INSERT and avatar updates. Authenticated owner staff actions use `ctx.supabase` for INSERT and UPDATE; authenticated manager actions read and update staff and invoke a schedule RPC. The accepted `20260521000001_data_api_explicit_grants.sql:68-69` grants authenticated and service roles SELECT/INSERT/UPDATE/DELETE; current owner and manager RLS policies gate direct edits. The proposed TEST change preserves that CRUD envelope and every policy/function/trigger. It does not try to narrow table-wide UPDATE to nine columns, because current owner workflows and historical grants require a separate field-level audit before that reduction.

| Role | Captured production table grant | Proposed standalone TEST table grant | Intentional difference |
|---|---|---|---|
| `postgres` owner | `arwdDxtm` | owner rights unchanged | Migration/trigger/maintenance authority remains with owner. |
| `anon` | `arwdDxtm` | **none** | Remove all direct staff table privileges; no anon policy or accepted direct anon staff operation was found. Server admin handlers retain their own authorization. |
| `authenticated` | `arwdDxtm`, plus nine column UPDATE ACLs | `arwd` | Preserve owner/manager CRUD under existing RLS; remove TRUNCATE, REFERENCES, TRIGGER, MAINTAIN. Redundant column ACLs are removed by the explicit LOCAL overlay. |
| `service_role` | `arwdDxtm` | `arwd` | Preserve server-side scanner/onboarding CRUD and RLS bypass as currently modeled; remove DDL/maintenance-like table privileges. Server credential must remain server-only. |

The TEST-only overlay is `tests/database/pr58-staff-test-privileges-overlay.sql`, SHA-256 `1420008E900A3F4EF63B6C198F6977B5559499BA1D9B50FF08727AA02E704BC5`. It applies explicit REVOKE/GRANT only to `public.staff`; no policy, ownership, function, trigger, schedule, or device definition changes. The redundant nine column ACL entries are removed. The current production mirror at `pr58-staff-current-contract-local.sql` remains unchanged. **Owner decisions before TEST application:** approve this explicit role matrix and hosting/Data API configuration; decide whether authenticated table-wide UPDATE needs a separate field-level restriction design; decide separately whether to investigate or remediate production's broad ACL. The retained table-wide UPDATE means a permitted operational-role row update could still edit identity/archive fields if the table is API-reachable; the nine historical column grants do not limit that table-level permission. This is inherited scope, not a new capability of the overlay. None of these changes is approved for remote application by this LOCAL test.
