The separate `/crm/master-sheet` page remains the audit, review, diagnostics, and source-inspection surface. Normal staff work remains in the existing Bookings and Cash Flow workspaces.

## 1. Existing Bookings consumers and data flow

**Repository fact.** The [Bookings server page](<../../src/app/(dashboard)/crm/bookings/page.tsx>) resolves the authorized Front Desk context and selected date, then loads canonical bookings, daily payment summary, and waitlist together. The [Bookings API](../../src/app/api/crm/bookings/route.ts) provides the same branch/date data for [SWR refresh](../../src/components/features/bookings/crm-bookings-view.tsx). The [Bookings workspace](../../src/components/features/bookings/bookings-workspace.tsx) feeds `WorkspaceBookingRow[]` into desktop and mobile presentations. The [desktop workspace](../../src/components/features/bookings/bookings-desktop-workspace.tsx) filters and selects canonical rows; the selected command pane and modal stack can mutate bookings and payments. The [canonical query](../../src/lib/queries/bookings.ts) reads `bookings` and canonical order/transaction summaries. A Sheet reference must never be cast to `WorkspaceBookingRow`, given a booking UUID, inserted into its `bookings` array, selected into the command pane, or sent to a booking action.

## 2. Existing Cash Flow consumers and data flow

**Repository fact.** The [Cash Flow page](<../../src/app/(dashboard)/crm/cash-flow/page.tsx>) resolves the authorized branch/date, awaits [getCashFlowData](../../src/lib/cash-flow/cash-flow-queries.ts), and renders [CashFlowWorkspace](../../src/components/features/cash-flow/cash-flow-workspace.tsx). That query reads canonical financial accounts, transactions, movements, cash sessions, booking orders, and bookings to assemble Today's Money, recent payments, ledger entries, cash drawer, and reconciliation figures. [TodayTab](../../src/components/features/cash-flow/today-tab.tsx) and [LedgerTab](../../src/components/features/cash-flow/ledger-tab.tsx) consume the canonical model. [Cash Flow types](../../src/lib/cash-flow/cash-flow-types.ts) carry actionable ledger/payment identities and numeric effects. Sheet evidence must never enter `RecentPaymentItem[]`, `LedgerRecordItem[]`, `CashFlowWorkspaceData`, or `getCashFlowData` aggregates.

## 3. Exact safe insertion points

**Proposed contract.** In Bookings, add a separately loaded, presentational Master Sheet reference source at the `CrmBookingsView`/`BookingsWorkspace` boundary. Desktop may interleave distinct Sheet reference rows by supported visit time in the [desktop list](../../src/components/features/bookings/bookings-desktop-list.tsx), while mobile gets the equivalent read-only reference card in its list. Keep the canonical `WorkspaceBookingRow[]`, selected booking state, counts, command pane, and action props unchanged. A click on a Sheet row may open only a read-only source-detail panel and may link to `/crm/master-sheet` by date/source reference; it must not use `bookingId`, canonical detail URLs, or any action handler. Rows with missing/unparseable time go in a dated “Time unknown” group rather than receiving an invented time.

In Cash Flow, add a separately loaded “Master Sheet payment evidence” section within the existing Ledger tab, visually aligned with the ledger but outside its canonical table, totals, row menus, payment modal, and closeout controls. A short Today-tab pointer to that section may be considered after browser QA; Sheet values do not appear in Today's Money cards or recent canonical payments. The Sheet section has its own loading, empty, unavailable, and date-window states. Cradle Flow remains unchanged and receives no Sheet row or state count.

## 4. Booking reference view model

**Proposed contract.** `SheetBookingReference` is a distinct, read-only presentation type with `kind: "sheet_booking_reference"`, `sourceType: "MASTER_SHEET"`, `readOnly: true`, `canonicalLink: "UNLINKED"`, mapped `branchId`/label only when confirmed, `businessDate`, optional raw-supported time, customer display name, attendant display text, service names and supported durations, source provenance, review warnings, `observedAt`, and optional advisory `possibleMatch`. Missing data stays null or “Unknown.” The attendant is evidence, not a staff assignment; a Sheet location is evidence, not a Home Service dispatch classification. It has no canonical booking ID, customer ID, staff ID, booking status, payment status, assignment, or mutation callback. Use the existing minimized [Sheet visit projection](../../src/lib/integrations/google-sheets/sheet-review-projection.ts) as input; do not pass parser raw rows to the browser.

## 5. Transaction reference view model

**Proposed contract.** `SheetTransactionReference` represents each supported payment-evidence channel on a Sheet visit: `kind: "sheet_transaction_reference"`, `sourceType`, `readOnly`, source/visit identity, date, customer display, channel (`Cash`, `GCash`, `Bank / QR`, or `Card / terminal`), nullable amount, ambiguity marker, warnings, mapped branch, and observation time. It must say **Sheet evidence only — not a recorded CradleHub payment**. A source value or marker is not proof of settlement, direction, allocation, account, or a posted transaction. No invented transaction ID, reference number, cash drawer effect, or financial status. Multiple channels on one visit remain multiple evidence entries tied to the same Sheet source, not multiple canonical payments.

## 6. WorkbookSource → branch mapping boundary

**Proposed contract.** Keep the [parser](../../src/lib/integrations/google-sheets/sheet-parser.ts) branch-agnostic. After the reader identifies `spreadsheetId` and the parser emits [SheetSource](../../src/lib/integrations/google-sheets/sheet-types.ts), resolve a server-only `WorkbookSource { workbookId, branchId, label, enabled, decisionStatus }`. Apply the mapping before creating branch-scoped operational DTOs. The source tuple is **workbook ID + tab + row span + source key + content fingerprint**; `sourceKey` identifies Sheet coordinates, and fingerprint identifies observed contents, never a CradleHub booking or transaction. The current browser-facing review projection omits `spreadsheetId`, although `SheetSource` contains it; the future adapter must retain workbook identity server-side and expose only the minimum safe provenance in the native DTO. Mapping failure, disabled source, or unresolved branch yields `BRANCH_UNKNOWN` and no native branch-scoped row. Review retains its existing unknown-branch audit behavior, subject to its authorization.

## 7. Provisional branch mapping mechanism

**Owner decision required.** Staff/owner must confirm the currently connected workbook’s operational branch. Only then may a server-side configuration entry explicitly mark it `decisionStatus: "PROVISIONAL"` and map it to the confirmed Main Branch ID. This is a project decision, **not** a fact inferred from Sheet structure. No hard-coded branch assumption belongs in the parser, client, or record fields. Configuration must be replaceable by workbook ID, require a known authorized branch record, and fail closed if missing or inconsistent. If a separate SM workbook is later confirmed, add a separate mapping entry without redesigning parsing or CRM presentation. If the provisional answer changes, update the mapping; Stage 1E never rewrites canonical history. No branch record or database migration is proposed for this stage.

## 8. Badge and source presentation

Both booking and payment references always show **MASTER SHEET** and **READ ONLY** on the row/card and detail panel. A secondary label shows “External reference” or “Sheet evidence” and the mapped branch; source tab/row span, observation time, warnings, and content fingerprint are available in read-only detail. Sheet rows may share spacing, typography, and table rhythm with CradleHub records, while using the badges and a source line to prevent mistaken identity. A missing mapping shows Branch Unknown in Review, not a fabricated native branch label. The [Master Sheet Review](../../src/components/features/crm/master-sheet/master-sheet-review.tsx) remains accessible as an audit surface, not a second operational queue.

## 9. Read-only action restrictions

No Confirm, Cancel, Reschedule, assign therapist/driver, Arrived, Start, Complete, No-show, Record payment, Refund, Delete, Edit, reconcile, or import control appears on a Sheet row. No Sheet row enters Cradle Flow, schedule, attendance, availability, customer detail, dispatch, cash-session, or financial mutation paths. Canonical server actions continue validating canonical identity and branch independently; the native Sheet endpoint exposes GET only. Merely hiding buttons is insufficient: discriminated types and selection paths must prevent Sheet source keys from reaching canonical commands.

## 10. Search and filter behavior

Use the selected branch/date and a clearly labeled Master Sheet source inclusion control in Bookings; “All” may show both canonical and Sheet references, while “CradleHub” and “Master Sheet” narrow the presentation only. Date and safe text search may apply to Sheet customer/attendant/service display fields; preserve canonical filter behavior for canonical rows. Do not manufacture Sheet status, delivery type, payment status, assignment, or “needs attention” semantics to satisfy the [existing toolbar](../../src/components/features/bookings/bookings-list-toolbar.tsx). Under those canonical-only filters, either show canonical results only with an explicit Sheet-excluded note, or keep a separately labeled reference subsection; the owner should choose the final UX. Cash Flow’s Sheet evidence section gets its own date, source, channel, and text filters; its filters never alter canonical ledger/KPI data. The current Ledger source control is display-only, so implementation must wire any new Sheet filter explicitly rather than assuming that control already filters data. Invalid/out-of-window dates return a distinct state, not “no Sheet records.”

## 11. Duplicate and POSSIBLE MATCH behavior

Show both records. `POSSIBLE MATCH` is an advisory label, never a link, suppression, merge, or second booking claim. A candidate requires a resolved same branch, exact business date, and conservative agreement on normalized customer display plus supported time and service evidence. Missing or contradictory fields mean no advisory match; multiple candidates remain “needs review” rather than selecting one. The read-only detail says “This Sheet reference may describe the same visit as a CradleHub booking; no records are linked.” Canonical counts stay canonical. No customer matching, automatic deduplication, or persistent match decision is in this stage.

## 12. Financial isolation

Sheet financial values remain external evidence in a separate collection/component. They cannot be written to `financial_transactions`, `financial_account_movements`, `financial_order_allocations`, or any booking order; they cannot alter Today's Money, recent payment totals, ledger inflow/outflow/net, cash drawer expected balance, cash reconciliation, revenue, or expense reporting. Display “—” for canonical net effect, not a computed Sheet effect. This prevents double counting even if a Sheet and canonical record describe the same real-world payment.

## 13. Canonical CRM failure isolation

Do not add Google Sheet loading to the Bookings page’s or API’s canonical `Promise.all`, or to `getCashFlowData` and its required-data error path. Canonical Bookings and Cash Flow render first from their existing sources. A separately authorized reference endpoint/resource returns `available`, `available_empty`, `outside_loaded_window`, `unavailable`, or `forbidden` without replacing canonical output. A Google auth, metadata, tab, parse, timeout, or mapping failure only changes the Sheet section to “temporarily unavailable” or the appropriate specific safe state. Never convert unavailable to zero visits or surface credentials/raw provider errors. Existing canonical controls remain operable while Sheet loading or retrying.

## 14. Performance and loading boundary

**Repository fact.** The current [reader](../../src/lib/integrations/google-sheets/sheet-reader.ts) selects current/previous weekly tabs for a supplied business date, or for today when none is supplied, through no-store GETs with a 15-second timeout per GET. [The review service](../../src/lib/integrations/google-sheets/sheet-review-service.ts) currently supplies no selected date and already records sanitized authorization, auth, metadata, tab-read, parse, adapter, and total timings. A native selected-date read therefore needs an explicit weekly-tab/window contract, including missing-tab behavior; it must not silently present an empty list. Calling a two-tab read for every Bookings/Cash Flow refresh could create avoidable Google latency and quota use.

**Proposed contract.** Load Sheet references independently after canonical page data, with a separate request keyed by authorized branch/date and a bounded response. Reuse the repo’s server-only access pattern, minimize the returned DTO, and avoid duplicate reads on routine UI rerenders. Measure p50/p95 canonical render and Sheet readiness, phase timings, calls per session, response bytes, timeout/error rate, and behavior with Google unavailable before setting retry and freshness limits. No cache, persistence, or snapshot architecture is approved for convenience. The installed Next.js streaming guide (`node_modules/next/dist/docs/01-app/02-guides/streaming.md`) confirms that sibling Suspense boundaries can resolve independently; the implementation can choose an independent client resource or an isolated server boundary after focused browser timing tests. A full-page loading boundary must not wait on Google.

## 15. Authorization

The Stage 1D [access correction](master-sheet-stage1d-access-correction.md) permits authenticated active Owner/management and Front Desk/CRM roles, including canonicalized legacy Front Desk aliases and resolved super-admins, via [canViewMasterSheetReview](../../src/lib/auth/crm-permissions.ts). Other roles remain denied. Every future native Sheet request must authenticate and authorize before token selection or Sheet read, then enforce the server-resolved branch against `WorkbookSource`; never trust a client-supplied branch ID alone. Owner cross-branch viewing, if offered, must use the existing authorized branch-selection policy; management/Front Desk remain scoped to their authorized branch. Denied requests return no Sheet data and do not invoke the Google provider. Browser DTOs contain no credentials, full raw rows, or secret configuration. Render external display text as text.

Focused pure tests: mapping unresolved/disabled/provisional/changed; source identity and changed fingerprint; booking/payment DTOs with missing or ambiguous fields; no canonical IDs/actions; conservative possible-match cases; date/window/search/source behavior; authorization and branch denial before provider invocation. Integration tests: canonical Bookings and Cash Flow data and totals identical with Sheet available, empty, and unavailable; independent Sheet failure; GET-only endpoint; no canonical action accepts a Sheet source key; no financial table write or aggregate effect. Exercise desktop/mobile reference presentation and read-only labels with component tests where they protect these boundaries. Run type-check, focused lint/tests, build, and diff checks after implementation. This planning stage runs documentation checks only.

Capture sanitized network/timing evidence and identify the target. No such browser QA was performed in Stage 1E planning.

## 18. Rollback

If later implementation fails its gates, disable or revert the native reference UI/endpoint and workbook mapping in the stage branch, leaving the existing Review page and canonical queries intact. A future accepted deployment would require its own rollback plan tied to its release commit. This design writes no canonical data, so rollback requires no data reversal. This document can be revised or reverted on the stage branch after owner review.

## 19. Deferred canonicalization/import work

Any conversion needs an explicit identity, conflict, ownership, audit, mutation, and rollback contract. No Sheet schedule projection or parallel staff/customer/service workflow is planned.
